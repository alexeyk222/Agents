# Разведка данных: от задачи до дашборда

**Назначение**: сквозной сценарий, в котором агенты harness'а проводят
разведку данных в корпоративном контуре — от постановки в Jira до мэппинга
атрибутов и дашборда. Пример: анализ транзакционных атрибутов витрины.

---

## Схема

```text
Запрос аналитика (ключ Jira / описание)
        ↓
1. ContextScout ── Jira → Confluence → Impala (метаданные) → локальный контекст
        ↓
2. OpenCoder ───── план разведки + список запросов → подтверждение пользователя
        ↓
3. ScientificAgent ─ профилирование (sql-queries, exploratory-data-analysis,
        │            jupyter-notebook, polars/seaborn)
        ↓
4. Мэппинг атрибутов по шаблону templates/attribute-mapping.md
        ↓
5. CoderAgent ──── дашборд / отчёт (HTML, ноутбук, PDF)
        ↓
6. CodeReviewer ── сверка цифр, SQL и выводов; фиксация в project-intelligence
```

---

## Этапы

### 1. Сбор контекста (ContextScout, только чтение)

- Jira: scope, критерии приёмки, связанные баги и эпик (`sources/jira.md`).
- Confluence: глоссарий, паспорт витрины, справочники (`sources/confluence.md`).
- Impala, уровень 0: список таблиц, колонки, типы, комментарии, партиции,
  статистика (`sources/impala.md`).
- Результат: ранжированный список источников + **черновой список атрибутов** +
  список расхождений и белых пятен.

### 2. План разведки (OpenCoder → подтверждение)

- Какие таблицы и партиции изучаем, за какой период.
- Какие проверки: заполненность, кардинальность, гранулярность ключа,
  допустимые значения справочников, согласованность с Confluence.
- Готовые SQL-запросы уровня 1–2 — пользователь видит их **до** запуска.

### 3. Профилирование (ScientificAgent)

- Запросы только с фильтром по партиции и агрегатами.
- Результаты сохраняются в ноутбук / `.tmp/` с текстом запроса рядом с цифрой.
- Для каждого атрибута: тип, % заполненности, NDV, топ значений (без ПДн),
  аномалии (пики, «заглушки» вроде `0`, `-1`, `'N/A'`, `1900-01-01`).

### 4. Мэппинг атрибутов

- Заполнить шаблон `templates/attribute-mapping.md`.
- Каждая строка: технический атрибут → бизнес-термин → источник определения →
  метрики качества → статус (подтверждён / расхождение / не найдено).

### 5. Визуализация и отчёт

- Дашборд: заполненность по атрибутам, динамика по партициям, распределения
  справочных кодов, карта мэппинга, список расхождений.
- Каждая цифра на дашборде воспроизводима запросом из этапа 3.

### 6. Проверка и закрепление знаний

- `CodeReviewer` сверяет SQL, гранулярность и выводы.
- Устойчивые факты (владелец витрины, особенности атрибутов, известные
  дефекты) — в `project-intelligence/` через `/add-context`.
- Найденные расхождения — пользователю как кандидаты в задачи Jira (агент
  задачи не создаёт без явной просьбы).

## Пример запроса к OpenCoder

```text
Проведи разведку транзакционных атрибутов витрины dwh.dm_transactions по задаче DATA-1234.
Сначала через ContextScout собери контекст из Jira, Confluence и метаданных Impala.
Потом предложи план профилирования с SQL-запросами и жди подтверждения.
Итог: мэппинг атрибутов на бизнес-глоссарий и дашборд с качеством данных.
```

---

## Критерии готовности

- [ ] Все атрибуты из `DESCRIBE` присутствуют в мэппинге.
- [ ] У каждого атрибута есть источник определения или пометка «не найдено».
- [ ] Метрики качества посчитаны на явно указанных партициях.
- [ ] Расхождения Confluence ↔ данные перечислены отдельно.
- [ ] Ни в отчёте, ни в чате нет сырых персональных данных.
- [ ] SQL-запросы приложены и воспроизводимы.
