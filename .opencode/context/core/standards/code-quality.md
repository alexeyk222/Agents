# Рецепт приготовления качественного Python-кода

## Назначение

Этот документ задаёт правила, которым агент должен следовать при создании и
изменении Python-кода.

Правила применяются ко всему новому коду. При работе с существующим проектом
агент сначала изучает его структуру, `pyproject.toml`, локальные инструкции и
принятый стиль. Более конкретные правила проекта имеют приоритет, если они не
противоречат прямому запросу пользователя.

Агент не должен без необходимости перестраивать существующий проект, менять
публичные интерфейсы или редактировать файлы, не связанные с задачей.

## Краткая памятка

- Одна функция выполняет одно логическое действие.
- Функции и методы называются глагольными фразами.
- Классы называются существительными и используются при наличии состояния,
  инвариантов или связанного жизненного цикла.
- Все функции и методы имеют аннотации типов.
- Код форматируется и проверяется с помощью Ruff.
- Типы проверяются с помощью MyPy.
- Тесты пишутся на pytest, покрытие измеряется через pytest-cov.
- Новый код сопровождается тестами; целевое покрытие — не менее 80%.
- Перед завершением задачи агент запускает доступные проверки и сообщает их
  результат.

## 1. Структура кода

### 1.1. Функции

Используйте функцию для выполнения конкретного действия или вычисления.

Функция должна:

- выполнять одно логическое действие;
- иметь явно определённые входные и выходные данные;
- быть достаточно небольшой, чтобы её назначение было понятно без изучения
  большого объёма контекста;
- по возможности не зависеть от глобального изменяемого состояния;
- отделять вычисления от ввода-вывода и других побочных эффектов;
- быть пригодной для изолированного тестирования.

Не разделяйте цельную операцию только ради формального ограничения количества
строк. Если функцию трудно назвать, описать или протестировать, разделите её на
несколько смысловых функций.

```python
def calculate_mean(values: list[float]) -> float:
    """Calculate the arithmetic mean for a non-empty sequence."""
    if not values:
        raise ValueError("values must not be empty")

    return sum(values) / len(values)
```

### 1.2. Классы

Используйте класс, когда сущность:

- хранит состояние между вызовами;
- поддерживает инварианты;
- объединяет данные и поведение с общим жизненным циклом;
- предоставляет несколько связанных операций над одним состоянием.

Не создавайте класс только для группировки независимых функций. В таком случае
используйте модуль. Для простых структур данных предпочтительны `dataclass`,
`NamedTuple` или `TypedDict` — в зависимости от назначения объекта.

Зависимости класса передавайте явно через конструктор или фабрику. Не скрывайте
их в глобальных объектах.

```python
from collections.abc import Callable, Sequence


MetricStrategy = Callable[
    [Sequence[float], Sequence[float]],
    dict[str, float],
]


class MetricCalculator:
    """Calculate model metrics using the supplied strategy."""

    def __init__(self, strategy: MetricStrategy) -> None:
        self._strategy = strategy

    def calculate_metrics(
        self,
        predictions: Sequence[float],
        targets: Sequence[float],
    ) -> dict[str, float]:
        """Calculate metrics for predictions and targets."""
        return self._strategy(predictions, targets)
```

### 1.3. Состояние и побочные эффекты

- Не изменяйте входные коллекции без явной необходимости и документации.
- Возвращайте новое значение вместо неочевидной мутации существующего.
- Изолируйте работу с файлами, сетью, базами данных, временем и случайностью от
  основной вычислительной логики.
- Передавайте такие зависимости явно, чтобы их можно было заменить в тестах.
- Не используйте глобальное изменяемое состояние.

## 2. Именование

### 2.1. Репозитории и файлы

- Репозитории называются в `kebab-case`: `ocr-baseline`,
  `data-processing`.
- Отображаемое название репозитория пишется на английском языке с заглавных
  букв: `OCR Baseline`.
- Python-файлы и модули называются в `snake_case`: `data_loader.py`,
  `model_trainer.py`.
- Имя файла должно отражать его основное назначение.
- Не используйте бессодержательные имена наподобие `helpers.py`, `common.py`
  или `misc.py`, если назначение модуля можно назвать точнее.

### 2.2. Объекты кода

- Функции и методы называются глагольными фразами в `snake_case`:
  `process_data`, `calculate_metrics`, `load_model`.
- Предикаты начинаются с `is_`, `has_`, `can_` или `should_`:
  `is_valid`, `has_permission`.
- Классы называются существительными в `PascalCase`: `DataProcessor`,
  `ModelTrainer`.
- Переменные и параметры используют осмысленные имена в `snake_case`:
  `user_data`, `model_weights`.
- Константы называются в `UPPER_SNAKE_CASE`: `MAX_ITERATIONS`,
  `DEFAULT_PATH`.
- Type variable называется кратко, но осмысленно: `ItemT`, `ModelT`.

Избегайте нестандартных сокращений и однобуквенных имён. Однобуквенные имена
допустимы в коротком математическом контексте или общепринятых конструкциях.

## 3. Форматирование и инструменты

### 3.1. Обязательные инструменты

| Задача | Инструмент |
| --- | --- |
| Линтинг и форматирование | Ruff |
| Статическая проверка типов | MyPy |
| Тестирование | pytest |
| Измерение покрытия | pytest-cov |

Не добавляйте Flake8, Black или isort параллельно Ruff без требования проекта:
дублирующиеся инструменты усложняют конфигурацию и могут конфликтовать.

Настройки инструментов должны храниться в `pyproject.toml`. Если проект требует
длину строки 79 символов, это значение задаётся явно, поскольку стандартное
значение Ruff отличается.

```toml
[tool.ruff]
line-length = 79

[tool.ruff.format]
indent-style = "space"
quote-style = "double"
```

Версию Python и набор правил Ruff выбирайте в соответствии с окружением и
требованиями конкретного проекта, а не задавайте наугад.

### 3.2. Стиль

- Следуйте PEP 8, если локальная конфигурация проекта не устанавливает иной
  согласованный стиль.
- Используйте четыре пробела для отступа. Не используйте табуляцию.
- Ограничивайте строки 79 символами, если проект не задаёт другое значение.
- Разделяйте функции и классы верхнего уровня двумя пустыми строками.
- Внутри класса разделяйте методы одной пустой строкой.
- Используйте двойные кавычки там, где это не ухудшает читаемость.
- Используйте f-строки для интерполяции значений. Не превращайте обычную строку
  без подстановок в f-строку.
- Не оставляйте пробелы в конце строк и лишние пустые строки.
- Доверяйте автоматическому форматированию Ruff и не выравнивайте код вручную
  пробелами.

### 3.3. Импорты

Импорты размещаются в начале файла после docstring модуля и разделяются на три
группы:

1. стандартная библиотека Python;
2. сторонние библиотеки;
3. локальные модули проекта.

Внутри групп порядок импортов контролирует Ruff. Не используйте wildcard-import
(`from module import *`). Избегайте импортов внутри функций, кроме случаев с
опциональной зависимостью, циклическим импортом или измеримой необходимостью
ленивой загрузки.

## 4. Типизация

- Добавляйте аннотации ко всем параметрам и возвращаемым значениям функций и
  методов, включая `-> None`.
- Аннотируйте атрибуты, если их тип нельзя надёжно вывести из присваивания.
- Используйте встроенный современный синтаксис: `list[str]`, `dict[str, int]`,
  `str | None`, если версия Python проекта это поддерживает.
- Используйте `Any` только на внешних границах или при отсутствии корректных
  типовых описаний. Не применяйте `Any` для обхода ошибок MyPy.
- Не добавляйте `# type: ignore` без кода ошибки и краткого обоснования.
- Не используйте изменяемые значения как аргументы по умолчанию.
- Явно обрабатывайте `None` и сужайте объединённые типы перед использованием.

```python
def append_tag(tags: list[str] | None, tag: str) -> list[str]:
    """Return tags with a new tag appended."""
    current_tags = [] if tags is None else tags
    return [*current_tags, tag]
```

## 5. Ошибки и валидация

- Проверяйте внешние данные на границах системы: в API, CLI, загрузчиках файлов
  и адаптерах внешних сервисов.
- Выбрасывайте конкретные исключения с понятным сообщением.
- Не используйте пустой `except` и не перехватывайте `Exception`, если ошибка не
  может быть корректно обработана на этом уровне.
- Не скрывайте ошибку возвратом фиктивного успешного результата.
- Сохраняйте исходную причину при преобразовании исключения с помощью
  `raise ... from error`.
- Не включайте секреты, токены и персональные данные в исключения и логи.
- Для библиотечного кода используйте логирование, а не `print`. Вывод в консоль
  допустим в CLI на уровне пользовательского интерфейса.

## 6. Комментарии и документация

### 6.1. Комментарии

Комментарий должен объяснять причину, ограничение или неочевидное решение, а не
пересказывать следующую строку кода.

- Размещайте однострочный комментарий на отдельной строке над связанным кодом.
- Для сложного алгоритма используйте несколько строк, каждая из которых
  начинается с `#`.
- Предпочтительный язык комментариев — английский.
- Обновляйте комментарий вместе с кодом. Устаревший комментарий хуже его
  отсутствия.

```python
# The provider accepts timestamps only with second precision.
normalized_time = event_time.replace(microsecond=0)
```

### 6.2. Docstring

Публичные модули, функции, методы и классы должны иметь краткие информативные
docstring на английском языке. Для приватных объектов docstring обязателен,
если их назначение, ограничения или поведение не очевидны из кода.

Docstring описывает контракт, а не реализацию:

- назначение объекта;
- аргументы, если их смысл не очевиден;
- возвращаемое значение;
- значимые исключения;
- побочные эффекты и важные ограничения.

Не дублируйте информацию, полностью выраженную именем и типами. Используйте один
стиль docstring во всём проекте. Для генерации документации рекомендуется
Sphinx с расширением `autodoc`, если проекту нужна публикуемая API-документация.

## 7. Организация проекта

### 7.1. Рекомендуемая структура

Структура адаптируется к масштабу проекта. Не создавайте пустые каталоги «на
будущее».

```text
project-name/
├── src/
│   └── package_name/
│       ├── data/          # Код загрузки и предобработки данных
│       ├── models/        # Код моделей и обучения
│       └── utils/         # Узкоспециализированные утилиты
├── tests/                 # Автоматические тесты
├── data/
│   ├── external/          # Данные внешних поставщиков
│   ├── interim/           # Промежуточные данные
│   ├── processed/         # Подготовленные данные
│   └── raw/               # Неизменённые исходные данные
├── models/                # Веса и экспортированные артефакты моделей
├── notebooks/             # Исследовательские Jupyter-ноутбуки
├── experiments/           # Конфигурации и описания экспериментов
├── assets/                # Статические бинарные ресурсы проекта
├── README.md              # Назначение и инструкции по запуску
└── pyproject.toml         # Зависимости и настройки инструментов
```

Основной импортируемый код находится внутри пакета в `src/`. Корневые каталоги
`data/`, `models/`, `experiments/` и `assets/` содержат артефакты, а не
импортируемый Python-код.

Большие, чувствительные или невоспроизводимые данные не должны автоматически
попадать в Git. Правила их хранения определяются политикой проекта.

### 7.2. Логические блоки Python-файла

Располагайте элементы файла в следующем порядке:

1. docstring модуля;
2. `from __future__ import ...`, если требуется;
3. импорты стандартной библиотеки;
4. сторонние импорты;
5. локальные импорты;
6. константы;
7. публичные классы и функции;
8. приватные вспомогательные классы и функции;
9. точка входа `if __name__ == "__main__":`, если файл является CLI.

Каждый файл должен иметь одну основную ответственность. Если файл объединяет
несвязанные сущности или его трудно тестировать изолированно, разделите его на
несколько модулей с явными интерфейсами.

## 8. Тестирование

- Пишите тесты для всего нового поведения.
- При исправлении ошибки сначала добавляйте регрессионный тест, воспроизводящий
  проблему, если это практически возможно.
- Проверяйте успешные сценарии, граничные случаи и ожидаемые ошибки.
- Тесты должны быть детерминированными и независимыми от порядка запуска.
- Не обращайтесь в модульных тестах к реальной сети, времени, базе данных или
  внешнему сервису. Передавайте зависимости явно и заменяйте их тестовыми.
- Не проверяйте детали реализации, если можно проверить публичное поведение.
- Используйте фикстуры pytest для повторяемой подготовки данных, но не скрывайте
  в них существенную часть сценария.

Целевое покрытие нового и изменённого кода — не менее 80%. Покрытие является
индикатором, а не заменой качественных проверок: тест без содержательного
утверждения не считается полезным.

Пример команд:

```bash
ruff format --check .
ruff check .
mypy src tests
pytest --cov=src --cov-report=term-missing
```

Пути и команды адаптируются к конфигурации проекта.


## 11. Статусы кода

Допустимые метки:

- `TODO` — запланированное улучшение;
- `FIXME` — известная ошибка, которую необходимо исправить;
- `HACK` — временное компромиссное решение с описанием причины;
- `WIP` — незавершённая работа; используйте преимущественно в названии ветки
  или pull request, а не в коде основной ветки.

Метка должна быть конкретной и по возможности содержать ссылку на задачу:

```python
# FIXME(PROJ-142): Preserve timezone information during CSV export.
```

Не оставляйте метки без объяснения и не используйте их вместо регистрации
задачи. `TODO.md`, `FIXME.md`, `WIP.md` и `HACK.md` создаются только тогда, когда
такой способ учёта принят в проекте. В остальных случаях используйте единый
трекер задач или файл `TECH_DEBT.md`, чтобы не создавать несколько
рассинхронизированных источников истины.

## 12. Порядок работы агента

### Перед изменениями

1. Изучить связанные файлы, тесты, `pyproject.toml` и локальные инструкции.
2. Определить минимальный набор файлов, необходимый для решения задачи.
3. Проверить существующие интерфейсы и не ломать их без явного требования.
4. Уточнить существенную неоднозначность, если разные решения заметно меняют
   результат.

### Во время изменений

1. Сохранять текущий стиль и архитектуру проекта.
2. Делать небольшие, связанные изменения.
3. Добавлять или обновлять типы, docstring и тесты вместе с кодом.
4. Не исправлять несвязанные проблемы без согласования.
5. Не добавлять зависимость, если задачу разумно решить стандартной библиотекой
   или уже установленным инструментом.

### Перед завершением

1. Запустить Ruff formatter в режиме проверки.
2. Запустить Ruff linter.
3. Запустить MyPy.
4. Запустить относящиеся к задаче тесты, затем полный набор тестов, если это
   практически возможно.
5. Проверить покрытие нового и изменённого кода.
6. Сообщить, что изменено, какие проверки выполнены и какие ограничения или
   нерешённые проблемы остались.

Если проверку невозможно запустить, агент не должен утверждать, что она
пройдена. Вместо этого нужно указать причину и дать точную команду для запуска.

## Критерии готовности

Изменение считается готовым, когда:

- реализовано требуемое поведение;
- код соответствует структуре и именованию проекта;
- публичные интерфейсы типизированы и документированы;
- ошибки обрабатываются явно;
- добавлены содержательные тесты;
- Ruff, MyPy и pytest проходят успешно либо ограничения честно зафиксированы;
- не внесены несвязанные изменения;
- README и другая пользовательская документация обновлены, если изменился
  способ установки, запуска или использования.

**Главное правило:** если код трудно протестировать, понять или безопасно
изменить, его следует упростить и разделить на более ясные компоненты.
